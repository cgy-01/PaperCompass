# GitHub CI 与版本交付

GitHub 负责检查代码、验证可运行的发布包、保存正式版本。服务器始终手动下载和更新，不向 GitHub 配置服务器 SSH、数据库或生产 OAuth 密钥。

## 日常开发与正式发布

| 操作 | 自动执行 | 是否创建 Release |
| --- | --- | --- |
| 推送开发分支 | 工作流校验、源码/私密文件检查、前端单元测试 | 否 |
| PR、推送 main、手动运行 CI | 上述检查，加后端、真实浏览器、发布包安装启动测试 | 否 |
| 推送 `v*` 标签，或手动 Release 选择已有版本标签 | 验证标签属于 main，完整 CI，发布经过测试的同一产物 | 是 |

普通提交不需要改版本号、创建标签或编写发行说明。main 的构建包只是保留 7 天的 Actions artifact，不是正式发行版。需要更长保留期和服务器更新时，再有意识地发布版本。

## CI 检查

- `tests.yml` 的 `Source and frontend checks` 检查有效的 Actions 上下文、shell 步骤、已跟踪文件、Python 语法和前端逻辑。
- 完整验证使用 Python 3.11、Node 22 和真实 Chrome；浏览器不存在会失败，不允许将整组浏览器测试静默跳过。
- 测试数据位于 runner 的临时目录，外部抓取/OAuth/LLM 用测试替身；关闭 Hugging Face 在线模型下载。CI 不访问生产数据，也不发起真实付费推理。
- 保持当前 Python 依赖声明，图标按 `package-lock.json` 执行 `npm ci --ignore-scripts`；不自动升级应用依赖。
- 从干净 checkout 生成发布包，使用独立临时虚拟环境验证源码安装、空查询库启动、版本化资源、两份用户文档、只读 API 和 MCP 工具。虚拟环境复用 runner 中已安装的依赖，但必须从解压包导入应用，不能误用 checkout 的源码。
- `CI passed` 是统一的最终检查名。可在 GitHub 分支规则中将它设置为必需检查；当前配置不强制所有日常提交必须走 PR，不自动改仓库的分支保护策略。

## 发布内容

GitHub Release 包含三个附件：

- `paper-compass-vX.Y.Z.tar.gz`：源码、模板、前端模块、文档及图片、部署参考、已有启动脚本，以及生成图标所需的锁定 Lucide 资源。
- `RELEASE_MANIFEST.json`：版本、精确提交 SHA、Lucide 版本和逐文件 SHA-256。
- `SHA256SUMS`：压缩包和外部清单的校验值。

不包含原始论文库、查询快照、用户/会话/行为库、模型权重、虚拟环境、日志、私人配置或 Git 凭据。包采用源码安装方式，未将独立 wheel 作为当前产品的交付承诺。

同一干净提交、相同锁定资源和相同版本参数可以生成字节一致的包。实际 Python 间接依赖仍由安装器解析；这不是完全离线、跨环境逐字节一致的依赖环境快照。安装后应使用 `pip check`，变更依赖需要单独验证。

## 创建正式版本

先确认 main 的完整 CI 已通过，再在本机执行，例如：

```bash
git switch main
git pull --ff-only
git tag -a v1.2.0 -m 'Paper Compass v1.2.0'
git push origin v1.2.0
```

这里只是示例，不会由日常提交自动执行。发布工作流重新验证标签对应的精确提交，使用该次完整 CI 的同一份产物，不重新打包另一个版本。标签支持 `v1.2.0-rc.1` 等预发布名称，预发布不会设为 Latest。

也可在 Actions → Release → Run workflow 中输入已经存在的标签。手动运行不创建标签，不能发布任意开发分支。已有 Release 的附件不会被覆盖。

附件先上传到草稿，全部成功后才公开。若中途失败留下草稿，先检查失败原因和附件，再由维护者删除未完成草稿后重跑；不要修改已正式发布的同名版本。修正正式版本应创建新标签。

## 服务器手动更新

在 GitHub Releases 下载指定版本的三个附件，在下载目录校验：

```bash
sha256sum --check SHA256SUMS
```

解压到新的代码目录，阅读发布说明并复用现有运行数据的绝对路径，再按照服务器既有流程手动安装/切换代码和重启。源码包自带所需 Lucide 文件，无需在服务器再次执行 npm 安装。Python 依赖仍需现有环境或按声明安装。

保留上一代码版本、兼容的依赖环境和查询快照，便于手动回退。不要清空或覆盖运行目录、账号库、收藏、密钥或采集水位，不要对包含这些数据的项目根目录执行无保护的 `rsync --delete`。部署代码不会自动运行 `update`、历史回补或全库重分类。

GitHub 工作流没有 SSH/SCP/rsync 远程操作、服务器主机地址或服务重启步骤，不会修改服务器定时任务。CI/CD 的启用不代表服务器已经更新。

## 旧工作流与故障排查

原 Pages 数据流水线、文档 Pages 发布和手动 PyPI 发布已移到 `.github/legacy-workflows/*.disabled`，仅供参考，不能被 Actions 执行。此配置不会创建数据分支、上传数据库、发送邮件或触发模型总结。

工作流表达式校验使用固定版本 actionlint；所有外部 Actions 固定到明确的官方提交。默认 token 只有源码读取权限，只有正式发布 job 获得 `contents: write`。fork PR 不使用生产 secrets。

失败时查看具体 job 和测试报告。日常分支的完整验证显示 skipped 属于设计行为；PR、main、手动 CI 或正式版本验证被跳过则由最终检查判为失败。只修改本地但未提交的代码不在 GitHub 检查范围内。
